# What WindowServer, SkyLight and QuartzCore want from a Metal device (study, 2026-11-05)

Read-only, done on the development Mac (macOS 15.7.3); nothing was changed on the test desktop. Method: the selectors a framework references (`tools/framework_selrefs.m` reads the framework's `__objc_selrefs` in memory and intersects them with the methods of the Metal protocols, marking those the plug-in's classes lack), the C strings of the loaded frameworks (`tools/framework_strings.c`), the imported symbols (`dyld_info -imports`), and the translator run over the shader libraries that ship in macOS (`tools/air_batch.c`). No code of Apple's was disassembled. A selector that appears in a framework is a reference, not proof of a call on the path that matters: what follows is a list of what to prepare, and what is verified is marked.

## Who does what

- **SkyLight** (WindowServer) has two compositors, `CompositorSW.cc` and `CompositorMetal.mm` (`kWSCompositorMetal`); the log line `WS current compositor : %s` and `/tmp/WindowServer.metalinfo.out` (written by a WindowServer state dump) tell which one runs. It does not pick a device itself: `metal_device != nullptr && "CoreDisplay failed to provide a MTLTDevice"` is an assertion, so a Metal compositor without a device from CoreDisplay would be fatal, not a quiet fallback. The device comes from `CoreDisplay_DisplaySurface_GetMTLDeviceSPI`, and SkyLight imports `CARenderMTL*` (SetState, SetDestinationTextures) from QuartzCore: the drawing is QuartzCore's, SkyLight composites groups, shadows and ripples with its own shaders (`SkyLightShaders.air64.metallib`).
- **CoreDisplay** finds the device through the display's accelerator: strings `Failed to create MetalDevice for accelerator %d %#llx`, `Display accelerator changed`, `Service Port 0x%x, Accelerator Port 0x%x`. QuartzCore matches it by registry ID: `Could not find Metal device with registry id %llx`, and `Mismatched MTLCommandQueue and MTLDevice`. So the `RedNaviFB` framebuffer must point at `RedNaviAccel2` (the `rednavi_accel_link` stage) and `-[MTLDevice registryID]` must be the accelerator's registry entry ID (the device inherits it from the superclass; not yet checked against the framebuffer's `IOAccelIndex` link).
- Switches found as strings (not tried): the boot-arg `-disable_ws_acceleration` (CoreDisplay), the preference `BootToMetalCompositor` (SkyLight), QuartzCore environment variables including `CA_DISABLE_GENERIC_SHADERS`, `CA_FORCE_GENERIC_SHADERS`, `CA_DISABLE_INPLACE_SHADERS`, `CA_DISABLE_PRECOMPILED_PIPELINES`, `CA_DISABLE_DIRTY_REGIONS`, `CA_DISABLE_OPAQUE_FRAMEBUFFER`, `CA_DISABLE_ENCODER_SHARING`. These are how to ask for the simpler paths while the plug-in is incomplete (inferred from the names).

## Device and queue calls seen in the frameworks

`name`, `registryID`, `location`, `isHeadless`, `isLowPower`, `isRemovable`, `peerGroupID`, `recommendedMaxWorkingSetSize`, `maxBufferLength`, `supportsFamily:`, `minimumLinearTextureAlignmentForPixelFormat:`, `newCommandQueue`, `newCommandQueueWithMaxCommandBufferCount:`, `newBufferWith{Length,Bytes,BytesNoCopy}`, `newTextureWithDescriptor:` and `...iosurface:plane:`, `newSamplerStateWithDescriptor:`, `newLibraryWith{File,URL,Source}`, `newRenderPipelineStateWithDescriptor:error:`, `newRenderPipelineStateWithTileDescriptor:...`, `newComputePipelineStateWithFunction:error:`, `newDepthStencilStateWithDescriptor:`, `newHeapWithDescriptor:`, `newSharedEvent`, `newSharedEventWithHandle:`, `newRasterizationRateMapWithDescriptor:`. The plug-in answers all of them (the device class inherits Apple's implementation of many; only what the plug-in overrides is the plug-in's behaviour).

## Not answered yet (verified: `respondsToSelector` is NO on the plug-in's classes)

- **Command buffer:** `encodeSignalEvent:value:`, `encodeWaitForEvent:value:` (shared events; both SkyLight and QuartzCore reference them; they are how WindowServer orders GPU work against the display and against clients). `newSharedEvent` is on the device list above but only inherited. This is the first thing to implement.
- **Render encoder:** `setDepthClipMode:`, `setVisibilityResultMode:offset:`, `textureBarrier` (SkyLight), and the tile shading calls (`setTile*`, `tileWidth/Height`, `dispatchThreadsPerTile:`) which only matter on GPU families that have tiles.
- **Compute encoder:** `setThreadgroupMemoryLength:atIndex:`.
- **Texture:** `newTextureViewWithPixelFormat:` and the `textureType:levels:slices:` variants (texture views: SkyLight and QuartzCore both use them), `newRemoteTextureViewForDevice:`, `newSharedTextureHandle`, `remoteStorageTexture`, `swizzle`, `compressionType`, `gpuResourceID`. **Resource:** `setOwnerWithIdentity:` (both frameworks). `gpuResourceID` also on pipeline and sampler states.
- **Library:** `newFunctionWithDescriptor:error:` (QuartzCore).
- `-[MTLLibrary newFunctionWithName:constantValues:error:]` is present but **ignores the constant values** (it returns the plain function): see the next section.

## The shaders (measured with `tools/air_batch`)

| library | functions | translate to SPIR-V | not translated |
|---|---|---|---|
| CoreDisplay `default.metallib` | 4 | 4 | |
| SkyLight `SkyLightShaders.air64.metallib` | 37 | 34 | 3, framebuffer fetch (`ColorInput`) |
| QuartzCore `default.metallib` (the AIR slice; the other twelve slices of the fat file are native GPU binaries) | 161 | 147 | 11 framebuffer fetch, 3 threadgroup memory (`ThreadgroupBuffer`) |

"Translates" means the translator produced SPIR-V that `spirv-val` accepted; none of it has run on the card, and the translator's output for a function is not checked against what it should compute. The framebuffer-fetch functions are probably the "in place" shaders (`fixed_frag_*`, `InPlaceAlphaUnpremultiply`) that the `CA_DISABLE_INPLACE_SHADERS` switch name suggests can be turned off (not verified).

**Function constants are the big gap.** QuartzCore's fragment and vertex functions are built from one generic source with function constants (`fc_generic`, `fc_framebuffer_fetch`, `fc_has_*`, `fc_color_opcodes`, `fc_texture_function`, `fc_blend_function`, ...; `air.function_constant` occurs in 7 of the library's modules, plus the strings `Metal failed to specialize fragment function` / `vertex function`). `newFunctionWithName:constantValues:error:` must therefore evaluate the constants and either pass them to the translator (SPIR-V specialization constants) or substitute them into the bitcode before translation. The `MTLFunctionConstantValues` object, the `air.function_constant` metadata and what the translator offers for it have not been looked at yet.

Other things the shader metadata shows: half precision everywhere (`half4` colours, `Dv4_Dh`), 3D textures (`color_cube0`), `texture2d<half>`, `air.compile.framebuffer_fetch_enable`, argument-buffer-like structs (`config_buffer`).

## What the fallback looks like

Strings, not traced: QuartzCore `CoreAnimation: Failed to initialize Metal or OpenGLES contexts!`, `CoreAnimation: failed to create Metal context!`, `Software renderer! Simulating crash!`, `Metal failed to load library / pipeline library / binary archive / render pipeline / compute shader`, `Command buffer allocation failed!`; CoreDisplay `Failed to create MetalDevice.`, `Fallback GPU Display Pipe failed`, `CoreDisplay is not detached because of forcing GPU fallback`; SkyLight `MTLRenderPipelineState creation failed for device %@`, `This typically indicates a Metal compiler failure.`, `Error from Metal: %@`, `No MTLDevice.`. What the strings suggest and what is not known: a failure to create a context or a pipeline is handled by reporting and, in some places, asserting; there is no sign in the strings of a retreat to software after a command buffer fails at run time (the software compositor is chosen at start, as a boot-time decision: `BootToMetalCompositor`). The plug-in therefore should not expect a command buffer error to be survivable: a failed command buffer in WindowServer is more likely a frozen or blank screen than a quiet fallback to software. This is the main risk of enabling it, and the reason to keep the SSH route to a boot-arg that turns it off (`-disable_ws_acceleration`, to be checked) and the emergency USB EFI.

## Function constants, as built (2026-11-05)

`-[MTLLibrary newFunctionWithName:constantValues:error:]` (and the completion handler variant) now keep the values with the function, and the pipeline creation hands them to the translator, which specializes the AIR as LLVM text before translating it (`translate_reflected_specialized` in the translator fork, exported to the plug-in as `rn_air_translate_stage_fc`; `RedNaviMTL/rn_air.h`). A resource that a constant switches off is not in the module's reflection, so the app does not have to bind it. Names are matched against the module's constants (the globals carry the C++ mangled name, `_Z<length><name>`). `MTLFunctionConstantValues` has no public getter: the plug-in reads the values through its internal class's `newIndexedConstantArray` and `newNamedConstantArray` (private; used only if the object answers them, otherwise the function is refused with a message rather than silently left unspecialized).

Test (`tools/mtl_init_harness`, `RN_FC_TEST=<vk_fc.metallib>`, shader `mesa-bridge/test/vk_fc.metal`): an int, two bools and floats, one constant left undefined (`is_function_constant_defined`), and a texture argument that exists only when a constant says so. Three cases (by index; by name with one constant undefined and no texture bound; texture argument present) give 0 of 64 wrong each on the 7800 XT. Not tried: constants on vertex and fragment functions of a render pipeline (the same call path), vector constants, a real QuartzCore function with its real constant set, caching the specialized modules (every pipeline creation runs `llvm-dis` and the translator again).

## Events, as built (2026-11-05)

`newEvent`, `newSharedEvent` and `newSharedEventWithHandle:` on the device, and `encodeSignalEvent:value:` and `encodeWaitForEvent:value:` on the command buffer. An event's 64-bit value lives in a POSIX shared memory object (`/rnev.<pid>.<n>`, 4 KB, unlinked when the creating object goes away), so `signaledValue` and `setSignaledValue:` are atomic loads and stores that every process holding the event sees. `newSharedEventHandle` returns an `NSSecureCoding` subclass of `MTLSharedEventHandle` that carries the shared memory name; decoding it in another process and passing it to `newSharedEventWithHandle:` opens the same object. `notifyListener:atValue:block:` and `waitUntilSignaledValue:timeoutMS:` poll the value (200 us steps; a listener is dropped after a minute). Because a command buffer runs at commit, a signal record sets the value at its place in the order of the work, and a wait record blocks the committing thread until the value is reached (10 s, then the command buffer fails with a message).

Test (`tools/mtl_init_harness`, `RN_EVENT_TEST=1`) on the 7800 XT, all pass: initial value and set/read; a listener released by another thread; `waitUntilSignaledValue:` that is reached and one that times out; a command buffer that signals; a command buffer that waits for 11 (committed on another thread, held 300 ms: the blit after the wait had not run, then ran when the main thread signalled), then signals 12; the handle archived with `NSKeyedArchiver`, this program started again as a second process that decodes it, opens the event and adds 100 to its value; two objects of one event in a process.

Not verified: how QuartzCore and SkyLight use handles. They may use fields of Apple's own handle class or send it through XPC in ways a subclass does not satisfy, and a sandboxed client may not be allowed `shm_open` on a name it did not create (the system's own shared events work across processes through a Mach port). A listener's block is called from a queue after polling, not from the GPU; events that are signalled by the GPU while a command buffer is still running do not exist here (everything runs synchronously at commit).

## Texture views and the small selectors, as built (2026-11-05)

- **Texture views** (`newTextureViewWithPixelFormat:`, with `textureType:levels:slices:`, and with `swizzle:`): a view is a Vulkan image view (`rn_vk_image_view`) of the same image, with another format of the same texel size (images are now created with `MUTABLE_FORMAT`) and optionally `VkComponentMapping` swizzles; it shares the image, memory and host copy with its root (the root's `dirty` and `initialized` flags are used), so writes through one are seen through the other, also for IOSurface-backed textures. Only the whole of a 2D, one-level texture can be viewed (other ranges and types return nil with a log line); a view of another texel size is refused. `parentTexture` and `swizzle` answer. sRGB RGBA8 and BGRA8 are new pixel formats of the render path (as views or as textures). `vkCmdClearColorImage` clears in the image's format, so the clear colour is swapped when a BGRA8 view is cleared over an RGBA8 image (sRGB over UNORM clears are not corrected).
- **Answered without effect:** `setOwnerWithIdentity:` (textures and buffers; returns success), `gpuResourceID` (zero; textures, buffers, pipeline states, sampler states), `compressionType`, `setDepthClipMode:`, `setVisibilityResultMode:offset:` (logged once when a non-default value is asked), `textureBarrier` (logged once), `setThreadgroupMemoryLength:atIndex:` (logged; kernels with threadgroup memory arguments are refused by the translator anyway). `newRemoteTextureViewForDevice:`, `newSharedTextureHandle` and `remoteStorageTexture` return nil.
- **`newFunctionWithDescriptor:error:`** (and the completion handler variant) looks up the name and applies the descriptor's constant values; binary archives, options and `specializedName` are ignored.

Test (`tools/mtl_init_harness`, `RN_VIEW_TEST=<vk_texcopy.metallib>`), all pass on the 7800 XT: a kernel that reads a texture through a BGRA8 view, a swizzled RGBA8 view, a same-format view and a view of a view (0 of 240 texels wrong in each; the first two see red and blue swapped), a clear into a BGRA8 view of an RGBA8 texture (bytes 0 0 255 255), the refused views (8-byte format, level 1, a 2D array type), a pipeline from a function made with a descriptor, and the do-nothing calls inside a command buffer.

## The registry link between display and Metal device, checked (2026-11-05, read-only)

`tools/accel_registry.m` run on the test desktop (stage 3, WindowServer still on its software compositor):

- `MTLCopyAllDevices()` lists one device, "Apple", `registryID` 0x1000004d7 = the registry entry ID of `RedNaviAccel2` (the IOAccelerator service, child of the PCI device `GFX0`). So the device is the accelerator's registry entry, as QuartzCore's `Could not find Metal device with registry id` lookup needs. (Verified.)
- `RedNaviFB` (the IOFramebuffer) has `IOAccelIndex` 0, `IOAccelRevision` 2 (the accelerator has revision 2 too) and `IOAccelTypes` = `IOService:/AppleACPIPlatformExpert/PCI0@0/.../GFX0@0/RedNaviAccel2`, the service path of the accelerator. (Verified: the link the family's code reads is in place.)
- `system_profiler SPDisplaysDataType` already lists the RX 7800 XT with `Metal Support: Metal 3` and its display under it. (Verified: the display is tied to the GPU, and Metal support is reported as present.)
- Not known: whether CoreDisplay's own lookup (`Failed to create MetalDevice for accelerator ...`) succeeds, since it only runs when the Metal compositor is chosen. Two things differ from a real driver and might matter: `RedNaviFB` is a child of `RedNaviProbe`, which is a child of `GFX0`, where a real framebuffer is a direct child of the PCI device next to the accelerator; and there is a second framebuffer, `.Display_boot` (`IONDRVFramebuffer`, kept by `rednavi_keep_boot_fb=1`), which has no accelerator properties at all and is listed as a second, mirrored display. A Metal compositor that creates a device per display would find no accelerator for that one. Both are things to look at before enabling the Metal compositor, not things shown to be wrong.
- No WindowServer or CoreDisplay log line about Metal, accelerators or compositors was found in the unified log of the last three hours; the compositor in use could not be read from outside (`/tmp/WindowServer.metalinfo.out` is written by a WindowServer state dump, which was not triggered).

## QuartzCore's Metal renderer on the plug-in (2026-11-05)

`tools/ca_renderer_test.m` runs QuartzCore's own Metal renderer (`CARenderer` with a Metal texture and the plug-in's command queue) on the 7800 XT, in a normal process, without WindowServer. It draws a layer tree (colours, a rounded corner, opacity, a gradient, a shadow, an image) and writes a PNG; the same program on the development Mac's real GPU (`ca_renderer_test system out.png`) gives the reference. Run on the desktop: `RN_METAL_COMPUTE=1 RN_VK_DIR=... DYLD_LIBRARY_PATH=... ./ca_renderer_test RedNaviMTLDriver.bundle out.png`; `RN_LOG_CONSTANTS=1` logs the function constants QuartzCore passes, and the plug-in log (`/tmp/rednavi-metal-<uid>.log`) shows every function it asks for.

**What QuartzCore needed from the plug-in, in the order it ran into it** (each was a crash or an abort of the process):

1. `-supportsFamily:` and the other capability queries: the base class answers from tables a vendor driver fills in and called through a null pointer. They are answered by the plug-in now (Mac1/Mac2, Common1-3 and Metal3 yes, Apple GPU families no; `isFramebufferReadSupported` no, which makes QuartzCore pass `fc_framebuffer_fetch = 0`).
2. Device limits (`maxTextureWidth2D` and some forty more, alignments): the base class answered 0 ("greater than the maximum allowed size of 0" from texture descriptor validation). Answered with the values of this card as far as they are known.
3. The default library: `newLibraryWithURL:`, `newLibraryWithFile:`, `newDefaultLibrary` and `newDefaultLibraryWithBundle:` read the file themselves; a fat file takes the slice that is AIR.
4. `newDepthStencilStateWithDescriptor:` (an object, no depth test behind it), private SPI selectors on our objects (`-[MTLTexture protectionOptions]`, `-[MTLCommandBuffer setProtectionOptions:]`, `-[MTLBuffer initStandinWithDevice:bytesNoCopy:length:deallocator:]`): an unrecognized selector throws, so every class of the plug-in now answers an unknown selector with a zero of the kind the Metal protocols declare (and logs it).
5. The shader. `CA_DISABLE_INPLACE_SHADERS=1`, `CA_FORCE_GENERIC_SHADERS=1` and `CA_DISABLE_GENERIC_SHADERS=1` change nothing for the simplest fill (`fixed_frag_lpf_cpf` is requested either way); the framebuffer-fetch input was not requested by QuartzCore at all. It came from an argument that a derived function constant switches off: the arguments `dest_0..2` depend on `__metal_implicit_fc_pred_N` predicates that the Metal compiler computes in a static initializer (`air.static_init`) from the constants, with branches and phis. The translator evaluated that initializer only in a straight line and gave up at the phis, so the argument stayed enabled. `fc_static_init.rs` in the translator fork now interprets the initializer (integers, selects, phis, branches, `air.normalize_function_constant_predicate`, `air.is_function_constant_defined`; a constant nobody supplied is undefined and makes a predicate false) and writes the predicates it finds into the stores of the module before reflection.
6. The translator also adds placeholder resources for textures that are absent in a variant (`SynthesizedNullTexture`, `SynthesizedReadSampler`); the plug-in binds a 1 x 1 texture for the first and a sampler from the state the translator gives for the second.

**Result.** Three frames, no error; the picture has the background, the white square with its blurred shadow (the downsample and blur shaders run) and the orange image with its blue square, in the positions of the reference (CARenderer's output is upside down by design: the reference has the same orientation). **Differences from the reference, not understood yet:** the red rounded rectangle with opacity is not drawn, the gradient layer is white, and the colours are those of the source (orange 255 128 0) where the reference shows them colour-matched (about 240 130 50), so the colour management path (`fc_has_color_params`, colour opcodes, transfer curves) is not producing what it should; the first two are probably other variants of `fixed_frag` with constants the translator mishandles. Command buffer errors: none logged.

Still open from the list above: threadgroup memory, 3D textures, depth/stencil. The rollback script (`scripts/rn_rollback.sh`) and what is known about the `.Display_boot` framebuffer are in `docs/TEST_MACHINES.md`.

## QuartzCore on the plug-in, second round (2026-11-06)

With the single layers each drawn correctly (rounded rectangle, gradient, image, shadow alone), the combined scene was wrong: the shadow square was a transparent hole, the gradient flat green, the rounded corners square. What was found, in the order it was found:

1. **3D textures.** QuartzCore makes 3D textures (colour cubes) as soon as it takes the generic shader path; the plug-in refused them and QuartzCore dropped the draws that needed them. `rn_vk_image_create3d`, `replaceRegion`/`getBytes` with depth and 3D image views are in; the placeholder texture the translator asks for is 3D when the shader declares a 3D texture (the dimension rides in the upper bits of the binding kind). 3D textures are sampled only, never render targets.
2. **Device alignments.** QuartzCore lays its per-frame vertex/constant arena out with `minConstantBufferAlignmentBytes`; the plug-in left it to the zero stub, and the arena offsets went wrong: after the first generic draw QuartzCore restarted at offset 32 and overwrote the vertex data of the draws encoded before it (they run only at commit), so the first pass drew nothing. A real device (`tools/mtl_limits.m` lists its alignments, limits and about 250 boolean capabilities; run it with `system` or with the bundle path) answers 32 there, 4096 for `minBufferNoCopyAlignmentBytes`, 16 for the IOSurface alignments and 2 GB for `maxBufferLength`; `heapBufferSizeAndAlign` is `{length, 32}`. With these the offsets grow as they do on the real device and the shadow chain (82x72 source, three blur passes, the 126x116 shadow image) comes out right pass by pass.
3. **Reading the target as a texture.** The generic shader (`fixed_frag` with `fc_generic`) reads the destination through a texture bound to the render target when the device has no framebuffer fetch (`isFramebufferReadSupported` is NO here). A render pass is now ended and restarted (LOAD, with a barrier) around a draw that samples one of its own targets, and the draw after it.
4. **Buffers over the caller's memory** (`newBufferWithBytesNoCopy:`): copied into the RADV buffer before and back after each command buffer. Not exercised by anything yet.

**Still wrong.** The `fixed_*_gen` draws (generic shader, destination read as a texture) leave the destination as it was and add nothing: the white layer and the shadow are never composited in the last pass, the gradient is the first texel of its lookup texture, the rounded corners of a layer drawn through it are lost. Same function constants as the real device except that the real device has `fc_framebuffer_fetch` = 1 and picks the half variants (`lph`/`cph` against our `lpf`/`cpf`); the parameter buffers it binds have the same configuration words. Not yet known whether the translated generic shader (580 KB of SPIR-V, many branches on the constants) is miscompiled somewhere, or a sampler/texture binding is wrong. Options: implement framebuffer fetch (input attachments) so QuartzCore takes the same path as on the real device, or find the miscompiled part by cutting the shader down.

Debugging aids added: `RN_LOG_DRAWS` (passes and draws with viewports, scissors, textures), `RN_LOG_BUFFERS` (buffer bindings and bytes, and a note when vertex data is rewritten while the rest is encoded), `RN_DUMP_PASSES=<dir>` (PNG of every pass's first target), `RN_DUMP_SPV=<dir>` (SPIR-V of every translated stage), `RN_MAX_DRAWS=n` (only the first n draws of each pass), and, for `tools/ca_renderer_test` with `system` and `RN_TRACE_ENC=1`, a trace of what QuartzCore does on the real device's encoder.
