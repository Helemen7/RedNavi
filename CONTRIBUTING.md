# Contributing to RedNavi

Thank you for wanting to help. RedNavi writes to a real GPU from the kernel, so a change that looks harmless can hang a machine at boot. The rules below exist to keep every change small enough to review and honest about what was tested.

Read `README.md`, `docs/ARCHITECTURE.md`, `docs/ROADMAP.md` and `CLAUDE.md` (layout, conventions and hard-won facts) before you start.

## Before you write code

Open an issue first for anything larger than a bug fix: a new chip, a new subsystem, a change to the user client interface (`RedNavi/rn_uapi.h`) or to the build. Say what you plan to do and on which hardware you can test it. This avoids work that cannot be merged.

## Pull requests

- One topic per pull request. Support for a new chip, a fix in the Metal plug-in and new tools are three pull requests, not one.
- Work on a topic branch of your fork, not on its `main`.
- Rebase on the current `main`. A pull request must not contain merge commits.
- Each commit is one logical change, builds on its own and can be read in one sitting. As a guide, keep a commit of hand-written code under about 400 changed lines; a commit that needs more is usually several changes.
- Generated files go in their own commit, together with the generator and the exact command that produced them, so the reviewer reads the generator and not the output.
- The description says what the change does, how it was tested and on which machine, and what is still unverified. Do not write claims such as "no regressions" without naming what was run. A change that was not tested says so in its first lines: "not tested" is an acceptable statement, a claim without a test behind it is not.
- CI must pass (`make`, `make DEBUG=1`, `make test`).

A pull request that mixes topics or carries a commit too large to review will be sent back to be split. That is not a judgement on the work.

## Commit messages

The subject line is `Area: what changed`, in plain English.

- `Area` is the component or the milestone the change belongs to: `RedNavi`, `RedNaviFB`, `RedNaviAccel2`, `RedNaviMTL`, `mesa-bridge`, `compat`, `tools`, `docs`, or a milestone such as `M6`. A change that concerns the whole repository may leave it out.
- The rest is a normal sentence that says what the code does now. Examples from the history:

  ```
  RedNaviFB: keep every vertical blank registration (display link was 30 Hz in every mode)
  Hardware cursor: DCN cursor plane fed by RedNaviFB, no software cursor in the scanout
  ```

- This project does not use Conventional Commits. No `feat:`, `fix(scope):` or similar prefixes.
- The body, when there is one, explains why, and says what was verified on hardware and what was not.
- Every commit ends with a `Signed-off-by` line (see "Licence and origin of the code").

## What must not be in a pull request

- Vendor firmware in any form: the `.bin` files of linux-firmware, C arrays generated from them, disassembly. `LICENSE.amdgpu` allows binary redistribution only under its own terms, and this repository carries none. The firmware headers are generated locally by `tools/gen_*_fw_header.py` and are git-ignored.
- VBIOS images, raw EDIDs, ACPI tables (`DSDT`, `SSDT` dumps) and unedited `ioreg` output. They carry serial numbers or vendor code. Cut those parts out of logs before you commit them.
- Compiled files: executables, object files, kexts, `.aml`, `.exe`, `.dll`, `.DS_Store`. An executable is not reviewable and nobody can tell what it does. If you think the project needs one, open an issue first and say exactly what the file is, where it comes from, how it was built, what it is for and why the source cannot be committed instead.
- Any other binary file (an image, a capture, an archive) that the description does not declare. For each one the description says what it is, where it comes from and what uses it. An undeclared binary is a reason to send the pull request back unread.
- Paths, names and settings of your own machine: `C:\Users\<you>\...`, `/Users/<you>/...`, `D:\GIT\...`, drive letters, the location of tools installed on your computer. What is committed must work from a fresh clone with the documented steps (`scripts/bootstrap.sh`, `make`), on a machine that is not yours. A tool takes its input as an argument or a documented environment variable, not from a path written into the file.
- Pointers to reverse-engineering tools or to vendor binaries (disassemblers, decompilers, unpacked vendor drivers) as part of the workflow. See "Licence and origin of the code".
- Whole third-party header trees. Register headers of the Linux driver are not copied in: the registers the code uses are generated from them (`tools/gen_gc_regs.py`, `tools/gen_dcn_reglist.py`), and the generator and its output are committed. Headers of installed packages (Vulkan, for example) are taken from the package.
- Hand edits to generated files. Files that start with `// Generated by` are changed through their generator.
- Tooling that is not about the driver: installer creation, OpenCore configuration, USB mapping, machine-specific setup scripts.
- Changes to the files the whole repository depends on, mixed into another topic: `CLAUDE.md`, `README.md`, `CONTRIBUTING.md`, `.gitignore`, the `Makefile`, `scripts/bootstrap.sh`, `.github/` (CI) and the licence files (`LICENSE`, `NOTICE`). A change to one of them is its own pull request, with the reason in the description. The one exception is the line a change cannot work without (a new object file in the `Makefile`, a new generated header in `.gitignore`); say so in the description. `CLAUDE.md` holds facts about the project that were checked on hardware; it is not a place for notes about your own setup.

## Licence and origin of the code

RedNavi is BSD-3-Clause. By opening a pull request you agree that your contribution is under that licence.

- New hand-written files start with the two header lines the other sources have:

  ```c
  // SPDX-License-Identifier: BSD-3-Clause
  // Copyright (c) 2026 Helemen7 and RedNavi contributors
  ```

- Every commit carries a `Signed-off-by: Your Name <email>` line (`git commit -s`). With it you certify the [Developer Certificate of Origin](https://developercertificate.org/): you wrote the change or have the right to submit it under the project licence.
- Write code from scratch. Do not copy from NullMoth's kexts or plug-in (PolyForm Noncommercial), NootedRed, LegacyRed or any project whose licence is not compatible with BSD-3-Clause. The Linux amdgpu driver and FreeBSD's drm-kmod are references for ideas, register definitions and structure layouts (MIT); when a file takes definitions from them, say so in the file and in `NOTICE`.
- Do not disassemble or reverse engineer vendor firmware.

## Verified and unverified

Say what ran on hardware and what did not.

- A fact read in the Linux sources but never run here is marked unverified, in the code comment, in the docs and in the commit message.
- A claim about hardware behaviour comes with its evidence: the property read from the `RedNaviProbe` node, a register dump, a log. Put raw dumps in `docs/logs/<chip>/`, with firmware and serial numbers removed.
- A read of 0 from a block that must have a non-zero ID register means "powered down" or "wrong offset", not "works".
- This holds everywhere you write: the pull request description, commit messages, code comments, docs, issues and review replies. If you have no evidence, say that there is none. Words such as "works", "supported", "regression-free" or "compatible" describe a run you can show, not an expectation.

## Support for other chips

The development target is the RX 7800 XT (Navi 32, `1002:747E`). `docs/ADDING_A_GPU.md` describes the steps, from the Linux capture to the row in the ASIC table. Support for another chip is welcome in `main` under these conditions:

- You own the hardware and have run the code on it. Commit the evidence first: the IP discovery table and the `ioreg` properties of the probe from your machine, and, when possible, the Linux reference dumps (`tools/linux_collect.py`), in `docs/logs/<chip>/`.
- You stay reachable as the person who tests that chip. The maintainers cannot test it, and code nobody can test will be removed when it gets in the way.
- Nothing changes for the RX 7800 XT. Code paths of the new chip are selected by the versions in the IP discovery table, not by assumptions, and every register offset names the Linux header it comes from (the `gc_11_0_0`, `gc_11_0_3` and later headers differ; see `CLAUDE.md`).
- The work arrives in steps that follow the bring-up order of the roadmap (discovery, PSP, SMU, DMCUB, display, GC, queues), one pull request per step, each with its evidence. Not as one pull request for the whole chip.
- Add the machine to `docs/TEST_MACHINES.md`.

## Use of AI tools

Code written with the help of an AI model is accepted under the same rules as any other, plus these:

- Say in the pull request that an AI tool was used and for what.
- You have read every line, understand it and can answer questions about it in review.
- You ran it on real hardware. Text that a model produced about what the code does is not evidence; the dumps and logs are.
- Anything the model stated about the hardware and you did not check is marked unverified.

## Build and test

```
sh scripts/bootstrap.sh
make DEBUG=1
make test
```

After removing code from a kext, run `nm -u` on the binary: an unresolved symbol of our own links fine and then freezes the boot. Big local structures in kernel code are `static` (the kernel stack is 16 KB).

## Safety

Test on a machine whose display does not depend on the card under test, keep SSH enabled and keep a USB copy of the OpenCore EFI without the kexts. Every stage that writes to the card stays opt-in through a `rednavi_*` boot-arg until it is proven. Do not read whole register lists of the display block: clock- or power-gated blocks hang the machine.
